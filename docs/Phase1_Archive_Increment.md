# Phase 1：首个 DAT 只读资源层增量

2026-11-06，用户审核 Phase 0 后实施。交付独立 Rust /1 DAT 库与 CLI；这是 Phase 1 的第一步，不是完整 Phase 1、游戏运行器或 APK。

## 已实现

- `nekopack-archive`：小端头部和目录/文件哈希索引；非零 key 的 parity 校验；索引计数、块边界和重复长度检查；完整解密索引；按条目序号读取前缀或流式解密整个资源。
- 逐字节/u16 lane 反馈解密，支持奇数尾字节、跨读取边界继续状态、零 key 明文块。不同资源重新初始化 key，不从密文中点无状态解密。
- `u64` 块偏移，资源块之间按实际长度相邻；不把内存解密对齐误用为磁盘对齐。
- 重复哈希原样保留；尾随字节数报告给调用方；不猜测同名覆盖策略。
- `nekopack-cli`：`inspect-archive` 输出 TSV，`read-index`/`read-entry` 输出二进制。资源读写错误返回非零状态，诊断走 stderr。

库不依赖旧 Python 研究项目、不依赖外部 crate，不调用 Windows 引擎或任何私有运行时。库只要求 Read + Seek，资源输出要求 Write。打开后源文件不得被修改。

## 验证与证据

自动测试：12 项库测试、2 项 CLI 集成测试通过。包含外部参考解码器生成的固定向量（不只测自己加密后自己解密）、全部字节切分位置、奇数长度、加密索引、截断、计数越界、错误 parity、输出失败、重复哈希、跨 64 KiB 缓冲、以及不分配巨型文件的 >4 GiB 稀疏源测试。Phase 0 的 6 项 Python 回归测试也通过。

格式检查 `cargo fmt --all --check`、静态检查 `cargo clippy --workspace --all-targets -- -D warnings` 通过；release 已构建。环境为 Windows GNU、Rust 1.99.1；未构建 Android target。

真实数据差分见 [rust-archive-verification.json](../research/rust-archive-verification.json)：

- 四部曲 22 个包的原始 SHA-256 与 Phase 0 清单一致。
- 完整解密索引与旧 Python 参考实现逐字节相等。
- 51,201 个条目的目录/文件哈希、序号、偏移、长度、key 和最多 16 字节解密前缀相等。
- 所有包头/资源块非零 key 的 parity 检查通过（parity 不是内容校验和）。
- 完整 payload 使用确定性分层抽样：首/中/尾条目、最大条目、各长度模 8 类别及不同前四字节的首次出现；样本明文逐字节比较，仅将 SHA-256 和长度写入仓库。

完整 payload 比对共 **289 个资源、1,147,356,707 字节**，全部一致；各样本序号、长度和 SHA-256 均记录在报告中。

Rust 与参考 Python 使用不同实现路径，但都依据同一公开算法。这是实现差分，不是原版引擎行为认证。没有逐个完整解码所有资源，也没有进行 PNG/MNG 像素、Ogg codec、剧情或存档验证。

## 资源预算与限制

打开封包缓存解密索引和条目元数据，不缓存整个 DAT。CLI 索引预算为 16 MiB；资源拷贝缓冲固定为 64 KiB。库可由调用方设置索引预算。`read_prefix` 的分配上限由调用方参数决定，CLI 固定为 16 字节。

研究差分脚本会把抽样明文载入内存，用于逐字节比较，内存行为与 Rust 流式 API 不同。第一部五个 voice 包的未知目录 EFFB4B01 各有 193,148,025 字节条目，其用途未知；不能按目录或文件扩展名将这些条目默认为音频。

解析器显式针对本轮 /1 布局，不声称从单一魔数识别引擎版本。/2、/3、文件名编码/哈希还原、跨包挂载、补丁覆盖、MNG 解码、音频解码与 VM 都尚未实现。非零 key 不符合已验证 parity 规则时直接报告错误，不静默尝试另一个解密器。

## 复现

见 [README](../README.md) 的编译、命令与差分命令。合成测试仅需 Rust；本机真实样本差分另需用户游戏与旧研究参考工具。游戏资源、解密正文和编译产物均不提交。

下一增量建议是文件名哈希查找与包来源清单，先核对 patch101 的覆盖关系，再实现 MNG 块元数据解析；保持与实际样本和原版证据对应，不开始虚构脚本指令。
