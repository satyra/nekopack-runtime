# 开发路线与 MVP

Phase 0 已交付六份调查文档、证据索引和只读静态检查结果。2026-11-06 用户审核后授权推进，现已交付 [Phase 1 首个资源层增量](Phase1_Archive_Increment.md)。未解决问题见技术研究和脚本分析；不能将“调查文档完成”表述为“全部语义已查明”。

后续已交付 [名称/覆盖关系/MNG 元数据增量](Phase1_Metadata_Increment.md)。Phase 1 仍缺像素解码、动画语义和原版行为对照，不将静态检查成功等同整个阶段完成。

## 分阶段门槛

1. **Phase 0：证据与样本。** 已完成三组参考源码静态调查、四部曲封包检查及 MNG 抽样。尚需原版启动、脚本和播放行为实验。审核本轮范围与风险后才能进入下一阶段。
2. **Phase 1：资源。** 先实现 Rust /1 索引和按资源随机访问，再做游戏目录识别、补丁来源追踪、PNG/MNG 与音频格式检查。验收四部曲资源清单、字节内容与独立工具对照，奇数长度、损坏包和未知字段正确报错。不得宣称只做 PNG 提取就完成 MNG。
3. **Phase 2：脚本。** 从真实启动与短剧情样本建立语法/语义规格，先 AST 与诊断，再 VM、变量/条件/调用/跳转/等待。验收原版轨迹一致，统计已知样本命令覆盖与未知语句。
4. **Phase 3：渲染。** 支持背景、立绘、文本、图层、样本实际转场与 MNG 控制。以原版同状态画面对照，明确透明度、坐标与时序偏差。
5. **Phase 4：音频。** 确定真实 codec 与循环信息，支持 BGM/语音/SE/env、暂停与等待完成。验收事件顺序和播放位置，不能只检查 OggS 魔数。
6. **Phase 5：Android。** Kotlin 游戏库/SAF/JNI/输入/生命周期、自有存档与设置，输出 ARM64 APK。验证授权持久化、导入、启动、前后台、保存重启恢复。
7. **Phase 6：兼容。** 四部曲按固定样本逐场景回归，再引入其他作者/年代/格式变种。记录所有失败，不以系列样本等同通用兼容。

## MVP 范围（设计提案）

资源研究 MVP：桌面只读检查器，完整列出四部曲资源、报告补丁覆盖、保留 MNG 控制元数据与编码问题。它不是最终游戏运行器。

运行器 MVP：一个已验证版本族、至少两款游戏的真实短剧情，从确认入口进入，支持背景/人物/文本、点击继续、一个真实选择分支、BGM/语音/SE、必要 MNG 动画及自有存读档，并交付 ARM64 APK。所有流程来自原脚本，不硬编码剧情。其余三维效果、视频、回想/鉴赏等若未实现，必须在遇到时报告；不能跳过后仍声称完整通关。

## 工作量估算

以下为工程判断，单位人周，假设一名熟悉 Rust/Android 与逆向的开发者，有可运行原版和 Android 真机；不是测量值或工期承诺。模块可部分并行，不能简单相加得出日历时间。

- 样本与动态逆向：4–10 人周，之后持续开展。
- archive：2–4；resource 与 compat 初始版本：2–4。
- image/MNG：4–10，取决于实际控制块与合成需求。
- script：4–8；VM/core：8–20，语义未明是最大不确定性。
- renderer：4–8；audio：2–5。
- save：3–6；Kotlin/JNI/Android 集成：4–8。
- 四部曲兼容回归：6–16，跨新引擎版本另估。

遇到未识别脚本语言、复杂原生扩展或 /2、/3 样本时重新估算。未评估特性不靠兼容兜底假装支持。

## 审核后建议首个增量

只做独立 Rust /1 只读解析器与 CLI、合成边界测试、四部曲样本差分。暂不建立十个空 crate，也不照搬旧 Ren'Py 转换代码。与 L1 对齐的同时必须引入独立参考输出，消除两个工具共享解码错误的风险。
