# PK02 格式与汉化覆盖层静态证据

本文记录 PK02 容器、资源读取重定向和当前本地样本的编码证据。它不表示游戏逻辑、系统界面、剧情或 Android 兼容已经完成。

## 分析边界与来源

分析只读取本地包和 PE 元数据，静态反汇编 DLL，比较原版与补丁资源的字节、语法分组和哈希。没有运行随游戏附带的 EXE/DLL，没有查看图片、回想或故事正文。

本地样本：

- 包大小：61,452,041 字节。
- 包 SHA-256：`f73c451ee5409f53218ffbc5a0bb6e9dbdec8e3696e05f8bdf6cc96545d1feac`。
- 根目录记录偏移：61,452,007（`0x03A9AEE7`）。
- 12 个目录、151 个文件；151 个文件均使用压缩标记 1。
- 顶级文件分布：`script` 101、`system` 25、`image` 17、`voice` 7、附加说明目录 1。

样本与分析产物不进入 Git。证据位于本地 `.local/sorakoi-import/analysis/`：

- `dll-disassembly.txt`：DLL `.text` 静态反汇编。
- `inspect_pk02.py`、`pk02-metadata.json`：目录遍历、raw LZ4 解码和条目哈希。
- `exe-diff-metadata.json`：两个 EXE 的 PE/字节差异。
- `compare_script_metadata.py`、`script-command-comparison.json`：脚本命令字节来源比较。
- `compare_system_metadata.py`、`system-source-comparison.json`：系统源码词法分组比较。

## 容器布局

所有整数为无符号小端整数，偏移均相对于整个文件起点。结构没有固定对齐填充。

文件头共 12 字节：

```text
+0   magic[4]       ASCII "PK02"
+4   root_offset    u64
```

目录记录：

```text
+0   child_count    u64
+8   file_count     u64
+16  child_table    u64
+24  file_table     u64
+32  name           NUL 结尾的原始字节字符串
```

`child_table` 指向 `child_count` 个连续目录记录。每条目录记录结束于其名称的 NUL 之后；下一条记录随即开始。子目录的子表、文件表通过各自的偏移访问，不要求紧邻该目录记录。

`file_table` 指向 `file_count` 个连续文件记录：

```text
+0   decoded_size   u64
+8   data_offset    u64
+16  compression    u8
+17  name           NUL 结尾的原始字节字符串
```

名称没有字符集标签。样本同时存在 ASCII 资源名和 GBK 附加名称，不能把所有名称预先按 CP932、UTF-8 或 GBK 解码后再查找。读取器保留名称字节，以 `/` 连接目录与文件；根名称 `.` 不加入公开路径。查询接口要求已用 `/` 连接的原始路径精确匹配，不改写字节；调用方需要规范化目录分隔符时，应在编码前或独立目录参数上进行。

有效完整路径示例：`script/story.txt`、`system/system.nut`、`image/actor/501E07E0`。哈希形式的文件名也是索引里实际保存的名称，不是 PK02 目录结构的字段。

DLL 证据地址（该 DLL 静态首选基址 `0x10000000`）：

- `0x100038E0`：校验 `PK02` magic。
- `0x1000455D`：从偏移 4 读取 8 字节根目录偏移。
- `0x10003C60`：读取 32 字节目录头，再读取 NUL 名称。
- `0x10003D12`：定位并递归读取子目录表。
- `0x10003D62` / `0x10003D90`：定位文件表，逐条读取 17 字节文件头和名称。

## 压缩与完整性边界

标记 0 表示原样存储，读取 `decoded_size` 字节。标记 1 表示 raw LZ4 block：高半字节表示 literal 长度，低半字节表示 match 长度减 4；长度 15 使用连续扩展字节，match 距离为小端 u16，允许重叠复制。

文件记录没有压缩长度字段，也没有每项校验和。解码器以精确的输出长度停止消费当前 block，不能把后续索引字节当作压缩长度信息。当前样本全部 151 项均能独立解码到声明长度。没有发现 PK02 载荷加密或索引加密。

`0x10003440` 是 DLL 的 raw LZ4 解码函数，`0x100048DA` 至 `0x10004930` 根据压缩标记选择 raw LZ4 或原样读取。未知压缩标记不应猜测兼容。

不可信文件边界必须检查目录/数据偏移、整数与输出长度、索引预算、目录循环、LZ4 match 距离和扩展长度。应用层另行限制单项输出大小。索引预算不是整个解压输出的内存预算。

## 查找与覆盖语义

DLL 的索引表按原始名称字节做 FNV-1a 哈希并进行字节匹配；没有 Unicode 规范化或字符集转换。`0x10004790` 把目录请求中的反斜杠替换成正斜杠，随后按目录段查找。文件名参数由 `0x10004310` 按原字节查找；目录参数规范化不应扩展为完整路径的逐字节改写。例如 CP932 的“ソ”编码为 `83 5C`，其中 `5C` 是文件名字符的一部分。普通名称匹配区分大小写。

`0x10003A00` 将同名目录递归合并，`0x10003B70` 对已存在的同名文件替换其文件记录；因此后加载的条目覆盖先加载的条目。

资源重定向入口 `0x10001690` 先构造 `./` 加目录参数，在该目录中查原始文件名；失败时对文件名执行 NEKOPACK 名称哈希，将结果格式化为 `%08X`，再查相同目录。该逻辑使 `image/actor/501E07E0` 等名称可覆盖原本按名字寻址的 DAT 素材。

样本 DLL 使用的名称 seed 为 `0x8C416067`，与样本原版 DAT 的 `name_seed` 相同；替换表及乘数 81 与现有 `name_hash` 相同。通用宿主应从关联 DAT 取 seed，不能将本样本的 seed、包名或路径写死。

`0x10001A10` 在覆盖资源未命中时调用原引擎读取函数。补丁包不是完整资源集合，缺项需要继续从原 DAT 解析。

该 DLL 只显式加载一个固定路径的包；没有多包扫描、文件名排序或优先级字段的实证。通用宿主若支持多个 PK02，应明确自己的稳定顺序和冲突规则，不能声称字典序或任意发现顺序就是原 DLL 规则。

## 编码实证与解码策略的适用范围

PK02 是字节容器，不能由 magic 推导载荷字符集。以下结论只描述当前样本。

101 个脚本均无 BOM、无 NUL，全部可严格按 GBK 解码，均不能严格按 UTF-8 解码。但文件内存在明显的编码混合：

- 含高字节的 `.` 命令共 528 行，其中 523 行能在对应原 DAT 脚本中找到完全相同的整行字节。
- 含高字节的 `?` 命令共 682 行，其中 681 行能在对应原脚本中找到完全相同的整行字节。
- 以上两组高字节命令行均同时是合法 CP932 与 GBK，合法性不能决定实际语义。
- 其他分组有 38,804 个含高字节的行，其中 11,981 行不是合法 CP932，而全部是合法 GBK。

因此，显示正文与保留的命令/资源参数需要在语法边界区分；不能先将整文件按 GBK 转成字符串，再把已破坏的资源名重新编码。

系统源码的六个同名原资源均可匹配；另有一份额外备份 `.nut` 无同名原资源。词法比较发现：

- 所有高字节代码标识符数量为零；原有高字节注释逐字节保留。
- `config.nut` 有 1 个高字节字符串，保留原字节。
- `message.nut` 有 12 个高字节字符串，其中 10 个保留原字节；2 个修改位于 `local name_t = <literal> + m.name + <literal>`，可验证为字符从 CP932 转为 GBK。
- `saveload.nut` 有 13 个高字节字符串，全部发生 CP932→GBK 转码，位于 `case`/`c` 的转换表。
- `system.nut` 有 1 个改动的高字节字符串，位于 `local t = <literal>`。
- `x_rooms.nut` 有 1 个保留原字节的高字节字符串；`select.nut` 没有高字节字符串。

系统文本数据也混合：`list_sg.txt` 的 194 个高字节 token 全部能在同名原资源中找到相同字节（9 种唯一 token），19 条分号注释逐字节相同；`x_music_list.txt` 为 14 条二列数据，其中 13 个高字节 token 全是新/改 token，资源 key 与显示字段应分别处理。

一种由当前证据支持的来源策略是：先按真实语法切分 token，原版同名资源中存在的同字节字符串/token 保留 CP932，新/改显示字符串使用 GBK；代码与原注释保持 CP932。系统 `.nut` 必须识别引号、转义、注释和双字节字符，不能把双字节尾字节 `0x5C` 误当转义符。`.txt` 应按其表格/命令结构分字段，不能直接套用 `.nut` 引号规则。

目前没有发现“保留原字节的 literal，其语义却已改按 GBK”的反例。不过，相同字节不能证明任意未来补丁都保留原语义；这一策略依赖可访问的原版资源及已识别的语法，仍需要具体调用点的测试。没有原版来源时，不能仅凭 CP932/GBK 都可解码就静默选择其一。

静态 EXE 对比显示原有代码与数据节字节完全相同，仅修改 PE 头并新增 239 字节 `.Silvana` 导入节以导入 DLL。DLL 自定义逻辑中未发现 CP936/CP932 文本解码钩子；不能将编码混合解释为已经证实的全局字符集切换。

## 读取器验证

`nekopack-archive` 提供 `Pk02<R: Read + Seek>`，公开原始字节路径、大小、数据偏移和压缩标记；容器读取器不负责载荷文本解码、DAT 哈希别名或跨包排序。

验证包括 stored/raw LZ4、重叠 match、最终 literals、嵌套路径的 `/` 精确匹配、CP932 尾字节 `0x5C` 名称的索引与读取、大小写、缺项、索引预算、截断、越界偏移/大小及非法 LZ4 match。可选本地测试通过 `NEKOPACK_PK02` 指定包；只检查每个输出长度，不展示内容。

本地验证：该 crate 19 项普通测试通过，1 项真实包测试按需执行；真实包全部 151 项成功读取。Python 独立解析也完成全部条目解码并记录 SHA-256。以上是容器层验证，不是兼容完成声明。
