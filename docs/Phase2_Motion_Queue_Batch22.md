# Batch 22：每角色动作队列与核心完成判定

本批实现 BLESS `012603:211` 的 `.img2 _ >>>>`，仍使用共用 Rust Runtime 和 Android SAF 原始 DAT。真机验收范围限定为从标题到第 502 页：第 501 页执行两段动作，第 502 页确认后续对白和稳定位置。未扩展 `.env`。

## 原版依据

`research/verify_original_motion_queue.py` 对既有 BLESS 原 EXE 校验 22 处指令，同时从原始 DAT 校验目标命令。结果见 `queue-batch22-original.json`。

- `0x438f18` 为每个 token 建立独立记录，默认时间为 250 ms；`0x43cbaf` 增加队列长度。
- `0x437c0c` 提交当前动作的永久位移，读取队首并推进索引。临时位移不写回稳定锚点。
- `0x438679` 在当前段到期时切换；`0x4b5558` 重设计时起点，`0x43868a` 将新段 elapsed 清零。因此迟到帧不会把超时时间带到下一段，也不会一次跳过多个有时长的动作。
- `0x43e610` 独立更新角色通道。`_ >>>>` 是先纵向下沉回位，再右移 200，最终 `[640,360] → [840,360]`；两段各 250 ms。

这是静态代码与资源证据，不是原版动态逐帧对照。原版哪些输入调用 drain-all 尚未完整追踪；本批保持已有提前继续提交最终位置的行为，不声称已确认原版跳过语义。

## 实现与接口

`scene::plan` 将支持的动作 token 按顺序保存；`motion::Queue` 为每个角色保存段列表、当前段和该段起点。`StorySession::page_frame` 接收单调、无总时长上限的 elapsed，先生成各角色位置，成功渲染后提交队列状态，并返回布尔 `finished`；只有所有角色完成时才为 true。重复时刻返回同一帧，回退时刻及过期页面请求被拒绝，取帧不推进脚本 PC。

页面 `motion.duration_ms` 是最长角色队列的**名义时长**，不是宿主截止时间。单段元数据保持旧格式；多段使用 `kind: queue` 和 `segments`。Android 通过同一 JNI 操作 8 获取帧和完成标志，收到 false 就继续调度，收到 true 才停止。切页与关闭沿用序号取消机制。

稳定场景保存最终锚点；帧渲染临时覆盖位置。提前继续会清除队列并保留最终锚点，不把下沉峰值遗留到下一页。

目前支持 `_`、`[]`、重复 `>`、重复 `[` 的有序尾部动作串。资源/层序可在动作串之前指定；动作后不接受资源、层序或绝对坐标。绝对位置与动作组合、速度参数、数字计数、混合符号和对白前多条命令反复修改同一正在运动的角色仍明确拒绝。没有实现未经验证的任意演出队列。

## 复现

使用既有 Rust GNU 工具链、NDK r27d 与 Android 构建脚本。独立参考工具与游戏资源由本机提供，不进入仓库。

- `research/verify_queue_batch22.py`：真实 CLI 重跑 502 页，比较前 500 页的 JSON/PNG，以及队列终点、下一页。
- `platforms/android/verify_story.py --until-boundary --allow-page-limit --games 0`：使用本批 502 页 reference，真机逐页、音频、转场与动作取帧校验；此处是明确的页数上限，不是假称触达未知指令。
- `research/verify_motion_frames.py --include-queue`：使用原始 DAT、独立 Pillow 合成和原版曲线重算每个捕获帧；根据实际请求时刻独立重建切段，不信任宿主完成事件作为像素正确性的依据。
- `research/verify_story_layers.py`：静态终点逐像素参考；不替代动态动作或完整 MNG 播放验证。
