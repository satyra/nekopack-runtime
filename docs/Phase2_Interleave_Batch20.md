# Batch 20：角色动作、BGM 与对白的交错调度

本批处理 BLESS `012501:120..125` 的真实执行阻塞：`.img1 SGVE00Aa []` 排入角色动作之后，脚本切换到 `.bgm BGM021`，再启动语音并显示对白。修改位于共用 Rust Runtime；继续通过 Android SAF 读取原始 DAT，仅使用 PGKM10 原生 ARM64 真机，不需要 Root。

## 原版依据与实现边界

`research/verify_original_motion_bgm.py` 校验 BLESS 原 EXE 与原始 DAT。`interleave-batch20-original.json` 固定原文件哈希、指令位置和代码片段哈希，并复核原 `message.nut` 的语音与画面更新顺序。

原音频解析路径在 `0x44600d` 释放原通道句柄，在 `0x446082` 加载具名资源，在 `0x4460f6` 调用声音启动路径，随后设置音量/声像。`0x44611c..0x44611e` 的短暂停顿通过导入表确认为 `Sleep(10)`；之后进入状态记录、清理和返回路径，而不是等待背景音乐播放结束。图像操作仍沿用先排队、在对白的 `Screen.Render` 更新中推进的已核实路径。

因此只放开“已排入角色动作之后的单参数具名 BGM”组合。运行时保留 `motions`，向宿主发出一次 BGM 启动请求；宿主回执后继续到语音请求，再到 Text 页面。BGM 与语音的回执均不会清除动作，也不会额外生成动作完成 ACK。动作依旧在页面帧通道运行，翻页时清理。

原阻塞是 `StorySession::advance` 对动作与对白之间所有非角色命令的保守拒绝，并非 BGM 解码失败。本批复用既有音频和动作接口，无需修改 Android/JNI 协议。无参 BGM、淡出、等待、转场与动作的交错组合保持原有保护；不因具名 BGM 已验证而一并放开。

静态代码证据不等于动态原版时间轴对照。Android 音频准备和回执存在设备开销；本批验证顺序与状态，不声明与原版完全相同的启动延迟、精确音乐采样同步或固定帧率。

## 状态与错误路径测试

新增集成单元测试对 `[]`、`>`、`_` 分别执行“动作→BGM→语音→对白→下一页”，验证：

- 等待音频启动期间重复 poll 返回同一请求，不能提前取页面帧。
- 错误或重复 token 不能完成当前请求；BGM、语音依次只发出一次。
- 两次音频回执之后仍只有原来的动作，页面保留 BGM 记录及语音名。
- 取 0、125、250 ms 帧不推进脚本；下一页清除动作和旧效果记录。
- 缺失音频明确报错并停止会话，不伪造成功回执。
- 动作后的等待、无参 BGM、显式转场和同角色重复动作仍拒绝。

单元测试的最小 DAT 只放入 `OggS` 标记，用于测试调度和资源读取路径，**不作为音频解码验证**。真实音频解码、哈希及启动顺序由手机回归另行核对。

workspace 测试通过，其中 Runtime 为 38 项；Clippy `--workspace --all-targets -- -D warnings`、格式检查和 14 项 Python 测试通过。原有隔离测试的显式忽略项保持原口径，不计为本批通过项。修改后的逐帧校验器重放 Batch 19 的 32 帧捕获通过，未改写历史报告。

## 剧情推进与验证入口

桌面原始 DAT 执行到 269 页。前 175 页 JSON/PNG 要求与 Batch 19 逐字节相同；第 176 页为 `012501:125`，带 BGM021、语音 `VE_012501_0003` 和角色 1 的静止计时动作。后续页面不应残留该动作。

下一处明确边界为 `012501:582`、深度 2、步数 1455，尚未支持的修饰符 `[[[[`。没有跳过该指令，也没有在本批扩展其他动作符号。

- `verify_interleave_batch20.py`：实际运行 release CLI、检查 175 页前缀、269 页数量、第 176 页状态和准确边界。
- `verify_story_layers.py --stationary-brackets --vertical-dip --rightward-motion --actor-filter --games-selected 0`：独立 DAT/Pillow 对照最终场景和转场目标图。
- `verify_story.py --games 0 --until-boundary --movie-completion secondary`：真机从标题推进，明确点击跳过电影，检查页面、原始音频、宿主演出、横屏显示和 VM 销毁。
- `verify_motion_frames.py --include-bgm-interleave`：要求第 56、57、60、159、176 页捕获齐全；逐帧独立合成，并检查第 176 页 BGM 启动→BGM ACK→语音启动→语音 ACK→动作开始的事件顺序，确保未等待音乐播完。
- `verify_motion_cancel.py --page 176`：在新交错组合后的实际动作期间切后台，检查取消、无迟到帧与 VM 清理。后台退出仍结束会话，不声明支持恢复。

原始游戏资源、帧数据、截图及 APK 均只保留在本地；历史批次报告不改写。

## 真机主回归结果

`interleave-batch20-native.json` 记录 BLESS 原生 ARM64 的 269 页完整有界回归。页面文字、元数据和 PNG 均通过桌面对照；138 个音频请求通过原始 DAT 哈希与播放器事件核对，`interleave-batch20-audio-evidence.json` 二次复核通过，没有只靠终止区间豁免的音频条目。开场电影播放 186 帧后明确点击跳过，随后继续章节，不声明本批验证自然播完。

第 56、57、60、159 页各捕获 8 帧，第 176 页捕获 7 帧，共 39 帧全部通过独立 DAT/Pillow 像素对照。269 页最终场景和 13 张转场目标图也通过独立图层重放，见 `interleave-batch20-frames.json`、`interleave-batch20-layers.json` 和 `interleave-batch20-effects.json`。第 176、269 页实际 UI 截图确认横屏画面及对白显示正常。

第 176 页新 BGM token=97，语音 token=98。BGM 启动与 ACK 同时记录，46 ms 后语音开始，47 ms 后语音 ACK，504 ms 后动作开始；音乐时长 125679 ms，明确没有等音乐播完。动作的采样为 0、17、68、114、159、207、250 ms，宿主 begin→finished 为 292 ms。BGM 准备、页面合成及上传仍带来可测开销，不把这些结果描述为原版时间轴完全一致或恒定 60 FPS。

正常执行到 `012501:582` 的 `[[[[` 边界，VM live bytes=0；结束会话后音频资源全部释放。APK SHA-256：`241b4a9486ec4c7871dd8e7d60e07bc173fd72e734bbb527513fdb33a6fabea4`。本批不运行模拟器或其他三部，不宣称完整游戏支持。

## 后台退出与最终核验

同一 APK 第二次从标题推进到第 176 页；新 BGM 与语音均按顺序启动、回执之后，动作显示初始帧和 17 ms 中间帧，再切后台取消。没有目标动作完成事件、迟到帧、第 177 页或错误；前面四处动作均正常结束，音频缓存清理完成，VM live bytes=0。见 `interleave-batch20-cancel.json`。

主回归还检查了 BGM 替换后的旧通道事件，未出现迟到的进度或完成回调。`interleave-batch20-final.json` 汇总同一构建、桌面与真机页面、逐帧像素、音频顺序和后台取消的交叉核验，以及报告和测试日志哈希。
