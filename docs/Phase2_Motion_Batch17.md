# Batch 17：BLESS 角色右移与并行对白

本批只运行 BLESS 和 PGKM10 原生 ARM64 真机。移动解析、坐标、插值和像素合成都在共用 Rust Runtime 中；Android 仅提供时钟、显示和输入。原始 DAT 仍通过既有 SAF 授权读取，没有修改游戏脚本或使用预解包图片。

## 原版语义与证据

`research/verify_original_motion.py` 检查本机 BLESS 原 EXE 的指令与常量，并用独立 DAT 读取器读取原 `system/message.nut`。文件哈希、指令位置及函数片段哈希记录在 `motion-batch17-original.json`，不提交原 EXE 或游戏素材。

- `0x43cea4` 的符号解析器把每个 `>` 累加到水平位移；`0x43d033..0x43d03b` 将累加值乘以 50。`>>>>>>>` 因此是相对当前位置向右 350 个逻辑像素。
- 图片命令解析器默认 duration=250 ms、accel=0。图片资源更换和后续符号移动是分开的队列项；`0x437c0c` 消费零时长项并启动带时长的移动。
- `0x438640` 用经过时间除以 duration。默认曲线为 `(sin((t-0.5)*pi)+1)*0.5`。位移计算先在以画布中心为原点的坐标系中截断到整数，再在绘制时加中心坐标；负坐标不能简单对屏幕绝对坐标截断。
- 原 `message.nut:286` 先播放语音；其 `291..321` 行对白循环不断调用 `Screen.Render()`，再绘制姓名和文本。`Screen.Render` 绑定路径调用 `0x440fec`，后者通过 `0x43e610` 更新活动移动。移动与对白/语音并行，不新增一个阻塞式移动 ACK。

这是原版机器码与原系统脚本的静态证据，尚未进行原版屏幕的动态逐帧对照。仅针对已核实的默认参数路径实现，不能据此宣称所有角色动作兼容。

## 共用实现

`scene::plan` 接受末尾由一个或多个 `>` 组成的参数；`motion.rs` 计算通用位移与插值，没有 BLESS 文件名、角色名或脚本行号分支。移动可伴随资源替换，也可作用于保留角色。纯移动默认保留图层顺序与已缓存的夜色滤镜；后续另一角色的静态入场会一起出现在该对白场景。

Page 的 PNG 和 scene 继续表示稳定的最终场景，便于 headless 回归；只有存在移动的页面增加 `motion` 描述。`page_frame(sequence, elapsed_ms)` 提供实际动画 RGBA 帧，校验页序号与单调时钟，不推进 PC、不消费对白、不改变重复 poll 的结果。提前确认对白会提交目标坐标并清理该页移动状态。新的帧接口通过 Android JNI operation 8 调用，同一条工作线程拥有 VM 与 Scene。

Android 在对白已经显示、语音已经启动时请求初始帧，再以单调时钟请求后续帧。最终帧不是脚本 ACK；“继续”仍由用户控制。取消、切后台或关闭会使页序号失效，丢弃迟到的显示回调；VM 销毁排在同一工作线程中的帧请求之后。此验证壳仍在后台时结束会话，不声称已支持后台恢复或存档恢复。

## 支持边界

仅实现末尾重复 `>`、默认 250 ms 与默认插值；数值简写、`<`、`_`、`[]`、速度/加速度选项、同一角色在下一句对白前排多个动作、移动与显式转场的组合均继续显式停止。不同角色可各持一个移动，数量受角色槽位限制，不引入无限队列。

BLESS 从标题经 movie 进入章节，在 `012402:72` 执行 `.img6 SGVE00Aa >>>>>>>`，随后加载 img4，并到达 `012402:76` 的乌鲁露对白。总计 56 页，前 55 页 JSON/PNG 与 Batch 16 完全相同。下一边界为 `012402:81` 的 `.img6 _`，深度 2、步数 417；没有吞掉该动作继续剧情。

## 验证方法

- `verify_motion_batch17.py`：真实原始 DAT 的完整有界执行、55 页前缀字节相等、56 页数量、准确下一边界和移动元数据。
- `verify_story_layers.py --actor-filter --rightward-motion --games-selected 0`：独立 DAT 读取、原脚本静态重放、Pillow 合成，验证全部 56 页最终像素/图层。该重放器不被视为通用脚本 VM。
- `verify_story.py --games 0 --movie-completion natural --motion-captures ...`：实际手机按钮推进、全页 JSON/PNG、语音/BGM 原始资源哈希及播放事件、真实横屏对白、移动帧记录与 VM 关闭。
- `verify_motion_frames.py`：独立原始图片、夜色运算和原版曲线，逐帧重建手机记录的全部移动 RGBA，验证初态、中间态与终态，并确认目标语音先于移动开始。
- `verify_motion_cancel.py`：再次从标题通过真实按钮推进，只主动跳过开场电影；在第 56 页调度移动后 80 ms 请求切后台，验证取消记录、无迟到帧/继续剧情、音频清理与 VM live bytes=0。

核心测试覆盖曲线、居中坐标的负数截断、端点、溢出、未知修饰符、缓存滤镜、重复 poll、错误页序号、时钟回退、提前下一页和未实现队列组合。workspace 测试包含已有显式忽略的隔离入口，不能把忽略项计作通过；实际隔离子进程由现有测试入口执行。

## 真机自然推进结果

`motion-batch17-native.json` 记录 PGKM10 / Android 15 / native ARM64，从标题到 56 页的实际按钮回归。电影自然结束：2497 帧、每通道 4590720 个样本，播放头耗尽后进入章节；22 个音频请求通过原始 DAT 哈希与播放器事件核对。正常终止停在上述 `_` 边界，受管 VM live bytes 为零。

第 56 页真实屏幕确认横屏、角色最终位置和对白可见。实际移动采样为 0、17、57、96、136、175、215、250 ms，共 8 帧；全部帧与独立 DAT/Pillow/原版曲线重建逐字节相等，见 `motion-batch17-frames.json`。其中最后一帧完成上传和显示时，墙钟经过 278 ms；250 ms 是逻辑动画时长，宿主逐帧合成/传输存在延迟，不能声称恒定 60 FPS 或精确 250 ms 屏幕呈现。

全部 56 页最终像素/图层通过独立验证；另外 4 张转场目标图通过相同独立方法核对，见 `motion-batch17-layers.json` 和 `motion-batch17-effects.json`。声音事件复核见 `motion-batch17-audio-evidence.json`。本批没有新增人工听音结论，也没有运行模拟器或其他三部。

## 取消回归与最终检查

`motion-batch17-cancel.json` 使用同一 APK，再次从标题推进到 56 页，途中明确点击跳过电影。移动已实际显示 0 ms 和 17 ms 帧后触发切后台，最后记录为 cancelled；等待后事件文件保持不变，没有 finished、下一页或错误边界。音频缓存已清理，关闭结果确认 VM live bytes=0。这验证了移动显示过程中的生命周期退出，并不等于压力测试或后台恢复能力。

最终 workspace 测试、32 项 Runtime 单元测试、Clippy `--workspace --all-targets -- -D warnings`、格式检查和 14 项 Python 测试通过。最初 Clippy 指出了新测试中固定长度切片的写法，改用数组切片后复查通过。逐帧验证器最初漏挂载存放场景脚本的 system.dat，补正后用同一次真机捕获数据重新执行，8 帧全部通过；没有把该失败运行算作验证成功。
